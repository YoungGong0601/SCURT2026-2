# 03. 프로젝트 규칙

> 2026-09-29, 상태: 초안 (**(제안)** 표시 항목은 연구자 확인 후 확정)
> **코드와 Unity 작업 규칙**의 단일 출처다.
> 프로젝트 범위는 [00-project-brief.md](00-project-brief.md), 설계 결정은 [ARCHITECTURE.md](../ARCHITECTURE.md), 작업 환경 규칙은 [Environment Setting Rules](../.claude/environment/Environment-Setting-Rules.md)에 있다.

## R1. 코드 원칙
- **R1.1 진실 단일성(Single Source of Truth)을 가장 우선한다.**
  - 값, 상태, 계산, 규칙은 **한 곳에만** 정의하고, 나머지는 그곳을 참조한다.
  - 예: 이동 속도는 이동 컴포넌트에만, 바라보는 방향은 한 컴포넌트에만, 맵 설정값(청크 크기, 반경, 시드)은 한 곳에만.
  - 문서도 같다. 같은 사실을 두 곳에 적지 않고 링크한다.
- **R1.2 SOLID 원칙을 따른다.**

  | 원칙 | 이 프로젝트에서의 뜻 |
  |---|---|
  | S 단일 책임 | 한 클래스가 바뀌는 이유는 하나뿐이다 |
  | O 개방 폐쇄 | 새 방식(새 입력, 새 생성 알고리즘)은 기존 코드를 고치지 않고 **추가**한다 |
  | L 리스코프 치환 | 같은 인터페이스의 구현체는 서로 바꿔 끼워도 동작한다 |
  | I 인터페이스 분리 | 인터페이스는 작게 (메서드 1~2개) |
  | D 의존 역전 | 구체 클래스가 아니라 인터페이스에 의존한다 |

- **R1.3 디자인 패턴을 쓴다.** 쓴 곳에는 패턴 이름을 한 줄 주석으로 밝힌다 (예: `// Strategy 패턴`).
- **R1.4 가능한 한 단순하게.** 연구자가 이해할 수 있는 범위 안에서만 진행한다.
- R1.5 **(제안)** 원칙이 부딪히면: 진실 단일성 > 이해 가능성 > 그 밖의 SOLID, 패턴 적용. 추상화(인터페이스, 패턴)는 실제 쓰임(교체, 테스트, 실험)이 있을 때 도입하고 이유를 한 줄로 적는다.
- R1.6 **(제안)** 프레임워크, DI 컨테이너, ECS, Job System/Burst, async/멀티스레드는 쓰지 않는다. 측정으로 병목이 확인되고 연구자가 동의한 경우만 예외.
- R1.7 **(제안)** 새 개념(예: Perlin 노이즈, 청크 좌표)은 한국어로 짧게 설명한다 (주석 또는 문서).
- R1.8 **(제안)** 측정할 수 있게 만든다. 성능과 결정론은 수치(ms, 개수, 해시)로 확인할 수 있어야 한다.

## R2. Unity 작업
- R2.1 **(제안)** 입력은 새 Input System(`Keyboard.current`)으로 읽는다. 옛 `Input.GetAxis`는 쓰지 않는다. 근거는 `ProjectSettings/ProjectSettings.asset`의 입력 설정이다.
- R2.2 **(제안)** `.unity` / `.prefab` / `.asset` YAML은 손으로 고치지 않는다. 실행 중인 에디터에 명령을 보내 바꾼다.
- R2.3 **(제안)** 파일을 추가하거나 고치면 에디터에서 리프레시하고 `console_status`로 **컴파일 에러 0**을 확인한다.
- R2.4 **(제안)** 패키지는 `manifest.json`을 손으로 고치지 않고 Package Manager API/CLI로 추가한다. 새 패키지는 연구자 동의 후에만.
- R2.5 **(제안)** 아트는 원본과 게임용을 나눈다. 규칙과 변환 방법의 출처는 [Art/README.md](../Art/README.md).
